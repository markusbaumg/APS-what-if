# Rendering-library study for the what-if dashboard

Scope: a self-contained HTML page generated by Python (`.venv`, Python 3.14) from the emulator's result
CSVs (43 `;`-columns, 3 header rows, ~325 loops per 6 h window, loops are ~1/min) and the optimizer's
`summary.csv`, published through the Claude Code Artifact tool (scripts only from cdnjs / jsdelivr / unpkg,
exact pinned versions >= 2 weeks old, <= 16 MB, light + dark, phone width) and also openable from disk.
Workload target: ~50 scenarios x 300 loops x 10 series per-loop data plus a scenario x metric summary.

Everything below was checked on 2026-10-16: the CDN URLs with `curl -I` (all HTTP 200), the publish dates
from the npm registry, the bundle sizes by download, and the rendering cost with a synthetic benchmark
(50 small multiples x 10 line series x 300 loops + a 50 x 12 heatmap) run in the user's Chrome.
Benchmark sources: `gen_bench.py` and `bench/*.html` next to this file (served locally, timings in `#out`).

## Recommendation

**Apache ECharts 6.1.0, one script from cdnjs, data embedded as columnar JSON by plain `json.dumps`;
no Python wrapper.** Reasons, in the order they decided it:

1. It is the only candidate that covers every chart form the dashboard needs in one 1.1 MB file
   (360 KB gzipped): linked zoom/crosshair across small multiples (`echarts.connect`, `axisPointer.link`,
   shared `dataZoom`), `brush` selection, `heatmap` + `visualMap`, `parallel` coordinates with brush
   filtering, bar/line/step/scatter, and a canvas renderer that is indifferent to 150 000 points.
   Plotly needs its 4.7 MB full bundle for `parcoords`; Vega-Lite needs three scripts and a `fold`
   transform for parallel coordinates; Observable Plot and Recharts have neither built in.
2. Measured cost for the target workload is the lowest of the full-featured libraries: 177 ms to draw
   50 panels x 10 series (canvas), 37 ms for a linked zoom across all 50, 10 ms for the heatmap, 220 DOM
   nodes. Plotly (SVG): 264 / 62 ms and 9 500 DOM nodes; Vega-Lite facet: 244 / 111 ms; Recharts 438 ms
   for the panels alone.
3. The columnar shape the Python side produces naturally (`{"t": [...], "bg": [...], ...}`) is accepted
   directly as `dataset.source` with `encode: {x: 't', y: 'bg'}`; no row objects, no long format. The
   embedded JSON for 50 x 300 x 10 is 0.99 MB raw (0.35 MB gzipped), far under the 16 MB limit.
4. Theming is data, not CSS: colors are passed in `setOption`, so one `matchMedia('(prefers-color-scheme:
   dark)')` listener that re-reads the CSS tokens with `getComputedStyle` and calls `setOption` again gives
   a *selected* dark palette (what the dataviz skill demands) instead of an inverted one. The built-in
   `'dark'` theme is not used (it is not the validated palette).
5. Everything is a JSON option object, which is exactly what a Claude skill that writes the page later
   wants to generate and diff; no JSX, no build step, no transpiler in the browser.

Second place is **Vega-Lite** (declarative, facet + `bind: 'scales'` interval selection gave linked zoom for
free and the spec is pleasant to generate from Python) but it needs long-format rows (3.25 MB for the same
data, or a browser-side `fold`), three scripts, has no native parallel-coordinates, and debugging a
compiled 50-facet Vega dataflow in an artifact is painful. **Plotly** is the fallback if the team prefers
its API: the `plotly-cartesian` partial bundle (1.46 MB) does everything except parallel coordinates, and
linked zoom comes free when the small multiples are *subplots of one figure* with `xaxis2: {matches: 'x'}`
(50 separate figures need a relayout fan-out, 62 ms measured, with an event-loop guard).
**Observable Plot** is the nicest *static* small-multiples renderer (`fx`/`fy` facets, `currentColor`
makes dark mode free) but has no zoom/brush (a re-render, 41 ms for 50 panels, is acceptable but hand
built), no heatmap scale legend linking, no parallel coordinates, and its UMD build requires a separate
`d3` script (verified: the bundle externalizes `d3`, `Plot.lineY is not a function` without it).
**uPlot** (49 KB, 16 ms to paint the same 50 panels, built-in cursor sync) is the right tool if a
*per-loop strip* for a 7-day window (10 000 loops) ever needs to stay responsive on a phone; it is
time-series only and only on jsdelivr/unpkg, so it would be an addition, not a replacement.
**React + Recharts** is not a fit for a Python-generated report (see the last section).

(SVG libraries: 2 600-9 500 nodes) matter: hover and resize cost scale with them.

## Embedding and size budget

* The emulator runs loops about once a minute (devicestatus ~1 record/min), so a 24 h window is ~1 300
  loops and a week ~9 000. 50 scenarios x 1 300 loops x 10 series is ~4.3 MB of JSON; a week is ~30 MB
  and breaks the 16 MB artifact limit. Design rule: the main page carries the summary (scenario x
  metric, a few KB) plus the `orig` series once and the per-scenario `emul` series only for the shown
  window, downsampled to the 5-min CGM grid for the overview strip. Per-scenario per-loop detail goes
  into separate JSON files published through the Artifact tool's `files` map and fetched on click
  (`fetch('data/<scenario>.json')` works both from the artifact origin and from a local `python -m
  http.server`; `file://` blocks `fetch`, so the local-disk variant inlines instead).
* `orig` columns are identical for every scenario of one window; ship them once and store only
  `emul` columns (and the `delta` series) per scenario; that halves the payload.
* Embed data as `<script id="data" type="application/json">...</script>` and `JSON.parse` it: it is not
  evaluated as code, survives `json.dumps` of NaN/Infinity being mapped to `null` (use
  `allow_nan=False` and replace beforehand), and only `</` needs escaping (`.replace('</', '<\\/')`).
  Round to 2-3 decimals in Python (`round()` before dumping); it cut the synthetic payload by a third.
* Compression is not needed below ~8 MB; if a week-long view ever has to be inline, `pako` (cdnjs) with a
  base64 gzipped blob brings 3:1, at the cost of a second script and a decode step.
* Python side: `string.Template` (stdlib) with `$DATA`, `$TITLE`, `$GENERATED_AT` placeholders is
  enough. Keep the HTML template as a file next to the generator, not as a Python string, so the Claude
  skill and a human can edit it. No Jinja, no plotly.py, no pyecharts: the option objects the page needs
  are 20-40 lines of JS each and depend on the CSS tokens at runtime, so they belong in the page.

## Chart forms for this dashboard (dataviz skill applied)

The skill's rule is form first, color last, hover layer by default, table twin always. Mapped onto the
emulator's outputs:

1. **Headline row (not a chart).** Stat tiles: agreement with the phone for the base replay (the noise
   floor, e.g. "96 % of 320 loops"), total insulin orig vs emul for the selected scenario (U and %),
   SMB count orig -> emul, loops at the autoISF cap. Proportional figures, sans, delta in text tokens
   with an arrow icon, never a one-bar bar chart.
2. **Scenario ranking: horizontal bar, emphasis form.** One metric at a time (selector in the single
   filter row above everything), scenarios sorted, all bars in slot-1 blue, the base scenario in the
   de-emphasis gray with a baseline rule, the selected scenario darker. Direct label the extremes
   only. Dozens of scenarios stay readable because this is a nominal list with one hue, not 50 colors.
3. **Scenario x metric heatmap.** Rows = scenarios (grid order, base first), columns = metrics, each
   column normalized in Python (z-score or rank within the column) because the metrics have different
   units, cell color = diverging blue (less insulin than phone) - neutral gray - orange (more); the raw
   value in the tooltip and in the table twin. ECharts `visualMap` is one scale per series, which is
   why the normalization happens in Python, not in the chart. Cap at ~12 metric columns; more goes to
   the table.
4. **Parameters -> outcomes: parallel coordinates.** One axis per swept parameter followed by one per
   headline metric, one polyline per scenario; all lines in gray at 40 % except the selected scenario
   (slot-1 blue) and the base (black/white ink). Brushing an axis range filters the ranking and heatmap
   (ECharts `axisAreaSelectStyle` + `axisareaselected` event). Never color the lines by rank or by a
   rainbow of scenario ids.
5. **Per-loop small multiples, one axis each, shared time.** Vertically stacked panels with a linked
   crosshair and shared `dataZoom`: bg (one line, slot-1) with target band; ISF orig vs emul; insulinReq
   orig vs emul; SMB orig vs emul as thin bars with a 2 px gap; TBR as step lines. Two series per panel:
   `orig` in the de-emphasis gray, `emul` in slot-1 blue, direct-labeled at the right end. A dual axis is
   never used: bg and insulin are separate panels. Comparing scenarios overlays at most three (the
   all-pairs cap of the palette); beyond that, facet by scenario.
6. **Where the decisions diverge: diverging bar over time.** emul - orig insulin per loop centered on
   zero, blue below / orange above, neutral gray for |delta| under the noise floor; this is the honest
   picture of "what the setting would have changed", loop by loop.
7. **Agreement histogram.** Distribution of per-loop deltas per scenario as a strip of small
   histograms, one hue; the base scenario's spread is the reference the others are read against.

Color: take the eight categorical slots, the diverging pair and both surface sets from the dataviz
`references/palette.md` (pre-validated for light and dark), define them as CSS custom properties on
`:root` with the `prefers-color-scheme` + `data-theme` guards, and have the page read them with
`getComputedStyle` when it builds the ECharts options. Status colors are reserved for the medical
guard-rail labels ("hypothetical", "not validated", "exceeds max SMB"), with icon + text. Every chart
gets a `<details>` table twin generated from the same JSON. Text (values, labels, legends) uses the text
tokens, never the series color. Run `scripts/validate_palette.js` only if a slot is changed.

## The React / Recharts alternative

Assessed and not recommended for a Python-generated report:

* It works in an artifact: React 18.3.1 + ReactDOM + **react-is** (the Recharts 3 UMD declares
  `react-is` as a third external; without it `Recharts` stays undefined, which the benchmark hit first)
  + Recharts 3.10.1, all on cdnjs; 50 panels rendered in 438 ms via `createElement` without Babel.
* But: React 19 has no UMD build on cdnjs (only `cjs/`), so the page is pinned to React 18 forever;
  JSX needs the 2.9 MB Babel standalone in the page or a build step; Recharts has no heatmap and no
  parallel coordinates; `syncId` links tooltips and the `Brush` across charts but there is no zoom;
  every chart wants row objects, so the Python side would reshape 50 x 300 rows per panel or the page
  would do it on load.
* Where it does fit: if the dashboard later becomes an *app* (the artifact runtime with the shared
  database streaming optimizer rows, filters as React state, per-row actions), a React shell is
  reasonable; even then the charts inside it should be ECharts instances (`echarts-for-react` is not
  on a CDN; a 20-line `useEffect` wrapper around `echarts.init`/`setOption` is enough). The
  Python-generated report and the live React page can share the same JSON contract.

## Decision summary

| | Choice |
|---|---|
| Library | Apache ECharts 6.1.0, `https://cdnjs.cloudflare.com/ajax/libs/echarts/6.1.0/echarts.min.js` |
| Renderer | canvas (default); `renderer: 'svg'` only for a print/export page |
| Data | columnar JSON in `<script type="application/json">`, `orig` once, `emul`/`delta` per scenario, 2-3 decimals, per-scenario detail as separate `files` when a window exceeds ~6 h x 50 scenarios |
| Python | stdlib `json` + `string.Template`, template HTML as a file; no plotly.py / pyecharts / altair |
| Theming | dataviz palette tokens on `:root`, re-`setOption` on `prefers-color-scheme` change |
| Optional add-ons | uPlot 1.6.32 (jsdelivr) for a week-long per-loop strip; Vega-Lite as the alternative if the team prefers declarative specs |
| Not chosen | Plotly (bundle size, parcoords only in 4.7 MB full build), Observable Plot (no zoom/brush, d3 external), Recharts (no heatmap/parcoords, React 18 lock-in) |
