# Python port vs phone algorithm: autoISF determine_basal comparison

Compared: `software/determine_basal.py` (APS-what-if, branch `nightscout-source`, plus the input layers `emulator_core.py`, `ns_source.py`, `ns_glucose.py`, `ns_iob.py`, `ns_profile.py`, `ns_meal.py`, `ns_settings.json`) against `plugins/aps/src/main/kotlin/app/aaps/plugins/aps/openAPSAutoISF/DetermineBasalAutoISF.kt` and `OpenAPSAutoISFPlugin.kt` (autoisf, branch `kusi/3.4.2.6-backports`). Line numbers are for those two branches; `Kt:` = DetermineBasalAutoISF.kt, `Plugin:` = OpenAPSAutoISFPlugin.kt, `py:` = determine_basal.py unless another file is named. Both repos were read only; nothing was edited.

## Verdict

The port is a faithful statement-by-statement mirror of the phone's algorithm: every formula, branch order and threshold in the glucose status, autoISF factors, prediction loop, SMB enable chain, SMB sizing and temp basal logic was verified identical, and the Nightscout input layer reproduces the phone's profile, IOB and meal data closely enough that the no-change replay already agrees on 97 % of SMBs and 95 % of TBRs. The remaining disagreement is not one bug but a handful of small, independent code differences that each flip a decision at a boundary: (1) the SMB interval tolerance is 12 s in the port and 6 s on the phone, which with the user's 1-min SMB interval and 1-min loops is the single most likely cause of SMB mismatches; (2) every `round()` that mirrors a Kotlin `round()`/`roundToInt()` uses Python's half-to-even instead of Java's half-up, which is systematic for `minZTUAMPredBG` (an average of two integers: 25 % of odd sums land 1 mg/dl lower in the port) and sporadic for insulinReq, deviation, expectedDelta, maxBolus and the zero-temp durations; (3) the port rounds `threshold` to a whole mg/dl while the phone keeps `min_bg - 0.5*(min_bg-40)` fractional, which for every one of the user's mmol targets (5.4 -> 68.6 vs 69, 5.5 -> 69.5 vs 70, 5.6 -> 70.4 vs 70) shifts the minGuardBG disable, the LGS branch, the `bg > threshold` SMB gate, blendPct and carbsReq; (4) `naive_eventualBG` keeps the oref0 `min(sens, profile.sens)` rule for negative IOB where the phone (autoIsfMode hard-wired true) always uses the autoISF sens; (5) the bolus-increment rounding adds +0.0001 before truncating where the phone floors; (6) `round_basal()` rounds to 3 decimals where the phone's is the identity, visible as 4th-decimal TBR noise whenever the activity-monitor ratio is in force. A further set of differences is real in code but inert for this user's settings (normalTarget 99 vs 100, autosens in the iobTH reduction ratio, autoISF target source, EvenOn/OddOff double rounding, :55 cancel, CGM-error early return, pump-step rounding of max_basal) and will surface in VDF what-ifs that enable autosens, TT sensitivity flags or multi-value targets; one of them (normalTarget) is currently masked by the `_overrides` pin of `low_temptarget_lowers_sensitivity`. One latent crash exists (`fractionCarbsLeft` referenced before assignment when `carbs == 0` and `mealCOB > 0`, a state the phone itself produces right after a carb entry passes the absorption cutoff). The residual ISF mismatches (179/180 and 311/319) are attributable to reconstructed glucose-status inputs (grid phase, deltas, dura, parabola), not to the autoISF code, with two small code differences in `ns_glucose.parabola_fit`. The echo transcripts differ in many places (unit conversion of the backport, number formatting, missing/extra lines) but none of the scraped tokens is affected; one scrape (`COB: 0,`) silently never matches on Nightscout. A correction to CLAUDE.md: the phone runs autoISF 3.2.1 code that labels itself `3.2.0` (`Plugin:142`); DetermineBasalAutoISF.kt is byte-identical between the 3.2.0 and 3.2.1 upstream tags, so no 3.2.1 algorithm feature is missing from the port.

## Confirmed differences

Kinds: **decision** (changes insulinReq/SMB/rate/ISF or rT.duration), **scraper** (echo text a core/ns_* scraper or validator depends on), **echo-only** (transcript/flowchart only), **emulator-default** (emulator-only knob or default, inert in a no-change replay), **input-availability** (Nightscout lacks the phone's input), **measurement** (how the orig column is obtained). "Live" = can fire in the user's current no-change replay; "latent" = needs a VDF, another user's settings, or a rare input state.
